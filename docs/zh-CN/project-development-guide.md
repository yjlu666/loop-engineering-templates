# Project Development Loop 使用指南

[English](../project-development-guide.md)

## 开始使用

1. 复制 [templates/project-development/](../../templates/project-development/) 整个目录到要开发的项目下，包括 `skill/`。
2. 填写副本的 `CONFIG.md`，通过各环节的 `enabled` 选择是否启用，保留完整列表和原顺序。
3. 检查第 1–7 环节的内置 skill，按项目需要调整。第 8–10 环节（`test-deployment`、`test-acceptance`、`production-deployment`）仅含元数据，启用前需填写项目实际的输入、执行做法、返回结果和通过标准，或将其禁用。这些流程须遵守 `LOOP.md` 的文档保留边界，验收和部署结果不要求写成报告文件。默认配置启用了全部环节，未填写的环节会阻塞执行。禁用环节可不填写。
4. 向 Agent 提出具体需求，并告诉它：`读取 <实例目录>/LOOP.md 并执行，直到完成、需要用户处理或达到循环上限。`

## Skill 目录

每个环节使用独立目录，以 `SKILL.md` 为入口。需要脚本、参考资料或资源文件时，在该目录内按需添加，并从 `SKILL.md` 引用；路径以该 skill 目录为基准。

```text
skill/<环节 ID>/
├── SKILL.md
├── scripts/       # 按需添加脚本
├── references/    # 按需添加参考资料
└── assets/        # 按需添加资源文件
```

内置 skill 提供精简的做法和通过标准，不依赖脚本或外部 skill。

## 内置 Skill

常规实现选择交给 Agent，使用已有项目文档作为上下文，仅针对关键缺口提问。委派和代码修复回退由 Loop 负责，skill 不额外引入审批关卡、强制 TDD、固定提交步骤或执行台账。

禁用前置环节时，可使用等价的已有上下文，不强制要求特定输入文档或文件名。测试验收需要明确的测试目标；禁用测试部署时，应提供已有目标或明确约定本地验收。

## 文档产物目录

默认仅按当前范围和已启用环节的需要，保留立项文档、需求文档、架构文档和技术方案，供人理解和长期维护项目。所有路径以 `LOOP.md` 所在目录为基准。立项文档放在项目级目录，架构文档放在大需求目录。大需求拆分后，每个子需求分别保存需求文档和技术方案。例如：

```text
<Loop 所在目录>/
├── LOOP.md
├── CONFIG.md
├── skill/
└── shop-docs/
    ├── project-brief.md
    ├── user-login/
    │   ├── requirements.md
    │   ├── architecture.md
    │   ├── password-login/
    │   │   ├── requirements.md
    │   │   └── technical-design.md
    │   └── password-reset/
    │       ├── requirements.md
    │       └── technical-design.md
    └── order-export/
        ├── requirements.md
        ├── architecture.md
        └── technical-design.md
```

各阶段 skill 根据当前范围和已有产物确定文档目录，并将路径随结果传递给后续阶段。重试和后续修改复用稳定的标识，原地更新文档。子需求不单独生成架构文档。需求按用户可感知的成果拆分，同一范围内的审查、测试、部署尝试和修复不单独拆成需求。

澄清、开发、审查、修复、验收和部署结果只在会话或 subagent 返回值中交接。默认不创建仅用于记录执行步骤、中间结果、验证证据或阶段交接的文件和目录，无论其名称或格式如何。验收标准写在需求文档中，验证方法写在技术方案中。执行时简要返回实际命令及结果、代码位置、测试结果或已有 CI／部署记录作为证据，阶段通过不以生成报告文件为条件。工具产生的诊断文件放在临时存储或项目已有的产物系统中，不放进长期维护的文档目录。

只有用户明确要求、项目已有要求，或存在明确的长期阅读需求（例如部署运维手册、使用指南）时，才增加其他文档。优先复用相关的维护文档，将长期有效的结论合并进去，不追加执行流水，也不按时间戳或提交哈希另存副本。上述规则同样适用于 subagent 和项目自定义的验收、部署流程。

## 拆分与后续 Loop

拆分、文档位置和后续提示词由对应阶段的 skill 在 `LOOP.md` 的文档保留边界内负责；`LOOP.md` 同时负责环节执行、委派、结果流转和循环次数限制。

1. **项目立项：** 生成项目级 `project-brief.md`，列出按执行顺序排列的大需求、各自范围和依赖。本轮只选择第一个大需求继续。其余每个大需求都在会话中向用户提供独立、可直接使用的提示词，从 `requirements-clarification`（需求澄清）开始。只有一个完整需求的项目不强行拆分。
2. **需求文档：** 当前大需求过大且可以合理拆分时，在父级 `requirements.md` 中保留整体范围和子需求索引，为每个子需求生成独立需求文档。本轮只选择第一个子需求继续。其余子需求的独立提示词在会话中提供给用户。根据用户选择和 CONFIG，从 `architecture-document`（架构文档）或 `technical-design`（技术方案）开始；两者均禁用时，从后续首个已启用阶段开始。架构文档不是技术方案的前置条件。按依赖排序，并在每条提示词中写明具体前置条件。
3. **架构文档（可选）：** 仅在该阶段启用且纳入本轮执行时，生成、修改或参照整个大需求的 `architecture.md`。保留共享契约，区分兄弟需求的规划与已经实现的行为。
4. **技术方案及后续阶段：** 只处理选中的子需求；未拆分时处理当前大需求。允许为其进行必要的共享改动和回归检查。项目自定义的测试部署、生产部署流程也遵循此范围。

新开 Loop 指使用同一份 `LOOP.md` 和项目文档开启独立执行或对话，不需要复制模板，也不自动启动兄弟需求。每条生成的提示词必须包含实际绝对路径、执行范围、依赖和起始阶段。相关 skill 提供提示词范式，执行时需为每个剩余需求分别填好。提示词仅在会话中提供，最终交接或提前停止时也要列出，不写入立项文档、需求文档或其他项目文件。

明确指定起始阶段后，本轮跳过之前的阶段，不修改 CONFIG，也不把跳过的阶段标记为通过。起始阶段必须已启用且所需输入可用，否则报告阻塞；后续按配置顺序执行已启用阶段。没有架构文档时，技术方案直接依据需求和项目上下文开展，将必要决策记录在技术方案中，不要求回到架构文档阶段。根据项目实际证据核实依赖是否完成，不假设其他 Loop 已经完成。

完成当前子需求不等于完成整个大需求或项目，结束时需明确完成范围和剩余执行提示词。文档保存范围与依赖，后续执行提示词只保留在会话中。

## 配置

配置独立保存在 [CONFIG.md](../../templates/project-development/CONFIG.md)，只包含以下数据：

| 字段 | 默认值 | 用途 |
|---|---|---|
| `max_iterations` | `30` | 正整数，因代码修复而从后续环节返回代码开发的最大循环次数 |
| `stages` | 全部 10 个环节 | 保留完整列表和顺序，通过 `enabled` 选择环节 |
| `stages[].id` | 见 LOOP 中的环节表 | 环节 ID，对应 `skill/<id>/SKILL.md` |
| `stages[].enabled` | 全部为 `true` | 是否启用环节，至少启用一个；`false` 时跳过该环节及其 skill |
| `stages[].use_subagent` | 全部为 `false` | 是否将整个环节交给 subagent |

固定顺序：立项 → 需求澄清 → 需求文档生成 → 架构文档生成 → 技术方案生成 → 代码开发 → 代码审查 → 部署到测试环境 → 测试环境验收 → 部署到生产环境。可按需启用其中一个或多个环节，跳过环节后，不强制要求其文档产物；可使用需求和项目中的等价上下文，仅在真正必要的信息缺失且无法自行确定时提问。

`use_subagent: true` 时，主 Agent 不读取该环节的 skill，将整个环节交给 subagent 自行读取、分析并执行，再依据返回结果判断下一步。`false` 时，主 Agent 自行读取、分析 skill 并执行该环节。该设置不会禁用环节内具体任务的 subagent：适合交给 subagent 的任务仍需委派，即使 skill 没有明确要求；skill 内明确要求的委派也必须执行。

代码审查要求由未参与实现、使用独立上下文的 subagent 执行。`use_subagent: false` 时，主 Agent 负责协调并派发 reviewer；整个阶段已委派给符合条件的独立 reviewer 时，由它直接审查，不再重复委派。reviewer 接收任务、变更范围和相关证据，不继承实现过程的整段对话。默认一个 reviewer 即可。自审不能替代独立审查；缺少独立审查能力时报告阻塞。需要修复的问题返回代码开发，修复后在下一次审查阶段重新独立检查。

## 回退与停止

- 环节通过后进入下一个已启用环节；本轮选中范围完成且从起始阶段起所有适用的已启用环节都通过，才算本轮完成。其余大需求或子需求交由后续独立 Loop 执行。
- 代码开发后的环节需要改代码时，返回代码开发，修复后依序重跑全部后续已启用环节。代码开发未启用则报告用户并等待处理。
- 不需要改代码的问题留在当前环节处理，处理不了则报告用户并等待。
- 只有代码开发后的环节因需要修复代码而回到代码开发，才算一次循环。达到 `max_iterations` 上限仍未全部通过时，停止并报告未通过的环节、具体问题和已尝试的处理，不得假装完成。

每次执行只处理本轮选中范围，不保存跨次执行状态。生成的文档保留需求拆分和依赖，不保存后续提示词或环节执行进度。新一轮按提示词指定阶段开始，未指定时从首个已启用环节开始。`LOGS.md` 初始无记录，只记录可复用的通用问题和已验证的解决方法，不记录具体需求的问题或执行过程。
